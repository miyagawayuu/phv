[English](improvement-plan.md) | 日本語

1.2.0 の作業で後回しにしたもの。実装を計測し診断するなかで見つかった(`bench/` のベンチマークの仕組み、
[security-audit.ja.md](security-audit.ja.md) の第 16 回と第 17 回の診断)。各項目に、触るコード、変更、起こりうる問題、
効果の測り方、規模(S: 数時間、M: 1〜2 日、L: 1 週間以上)を書いた。どの項目をどのリリースに入れるかは
[仕様](spec.ja.md)の §19 にある。このファイルは作業用の一覧で、入った項目と見送った項目は消す。

どの項目にも当てはまる規則: 仕様が約束する動作は、同じコミットで仕様を変えないかぎり変えない(変えてよいものは §18 に
ある)。性能に触れる変更には前後の `bench/results/*.json` を添える。セキュリティ上重要な項目はサイクルの最初に行い、
リリースの前にもう一度診断する。

クロージャーは計測して JIT の対象から外した: 本体が短く組み込み関数から呼ばれるので、ネイティブコードに入る費用の

## 計測済みのもの

1.2.0 では、この仕組みで次を計測した(`bench/results/6da479b.json` と `ae06940.json` の比較): 特別ページのキャッシュで
3 段深いページは毎秒 4,589 → 67,918 リクエスト、応答のあとの片付けで PostgreSQL のページの p50 は 1.61 → 0.90 ms、
準備済みの文の保持で SQLite のページは約 18% 速く、fat LTO でバイナリは 1 MB 小さく、マイクロベンチマークは 3〜9% 速く
なった。

1.3 のサイクルでは、リクエストの間で VM を再利用することを計測して見送った: VM を作って空の殻を捨てるのは約 0.43 µs で、
トップページの p50(230 µs)の 0.2%、ページの実行全体でも 2.4% にすぎない。1 語を echo するだけのページがトップページと
同じ速さで答えるので、リクエストの時間は VM ではなく HTTP の経路にある。リセットには、リクエストの何も次に残らない
ことを証明する負担が加わるはずだった。代わりに測ると、簡単なページの時間の約 4 分の 3 はクライアント・ループバック・
hyper のもので、サーバー自身の分は主に 2 回のスレッドの受け渡しとログのスレッドを起こすことに使われていた。ページ用の
スレッドプールとログのまとめ書きで、p50 は 8〜9% 縮み、毎秒のリクエストは 10〜12% 増えた。

型検査済みモジュールのキャッシュも計測して見送った: 取り込んだモジュールの本体とすべての宣言の検査は、テストのコーパスの
`phv check` の 1〜2.5%、ページの初回のコンパイルの 3〜4%、エディターの診断の 1% 未満にすぎない。型検査器は関数と
クラスに番号を振り、予算を数えるのをプログラム全体で行うので、正しいキャッシュには作り直しが要るはずだった。時間は
ほかにあった: 組み込み関数のシグネチャの解析(プロセスごとに 0.57 ms、`phv check` の約 4%)と、読み込みのファイル
システムの処理(解析ごとに 2〜5 ms、ページの初回のコンパイルの約半分)。1.3 では、組み込み関数のシグネチャを専用の解析器で読み(450 µs が 85 µs に)、読み込みは変わっていないファイルの
中身とハッシュを覚え、`phv check` は 1 つのプロセスで複数のファイルを受け付ける。
